Chairman's Verdict

Do both — but minimal versions. Build a lightweight CI and a single Dockerfile for bahuraksha-api. Skip Docker for the frontend, skip Docker Compose, skip GHCR, skip E2E in CI. The council converges on "7 days is too short to overengineer" but the First Principles Thinker and the Executor missed that a backend Dockerfile eliminates Render's build-env black box risk with ~5 lines of effort.

Where the Council Agrees

7 days is too late for complex automation. All five advisors agree that multi-service Docker Compose, matrix builds, GHCR publishing, and E2E in CI are out of scope. The time cost of debugging these exceeds their demo-day value.

Docker Compose is a trap right now. The Contrarian, First Principles, Outsider, and Executor all warn against it. The peer review round called out Response C (Expansionist) for treating demo week as a career pivot.

Demo rehearsal > CI sophistication. The Outsider and First Principles both emphasized that the team's highest-leverage activity is practicing the demo flow, not writing YAML.

Where the Council Clashes

GitHub Actions: build it or skip it? The First Principles Thinker and Contrarian argue CI adds zero value before demo day and risks YAML debugging time. The Outsider and Executor say a 15-40 line workflow is trivially fast to write and provides basic safety. The chairman sides with the Executor — 15 minutes is worth the fail-safe.

Docker for the backend: insurance or overhead? The Contrarian wants to Dockerize everything for portability. The Outsider and Executor say Docker adds failure modes. The chairman's middle ground: one Dockerfile for bahuraksha-api only (5 lines, eliminates Render env mismatch risk) but skip frontend Docker and Compose orchestration.

Blind Spots the Council Caught

Pre-recorded demo backup. Multiple peer reviewers flagged that no advisor mentioned a fail-closed video recording. If Render cold-starts into a 502 error or the projector can't display the browser, a 5-minute loom screen recording saves the grade.

Demo runbook checklist. The peer review round identified the need for a DEMO_CHECKLIST.md — a 10-line document covering: env vars, model artifacts, data seeding, `docker compose up` command, fallback URL for offline mode. Without this, a panicked teammate can't rebuild the stack.

Existing Docker infrastructure. The ml-pipeline/ already has a docker-compose.yml with profiles. None of the advisors checked what already exists before prescribing.

Full Advisor Responses

The Contrarian

You're 7 days from demo day and you're asking about CI/CD architecture? This is the precisely wrong question. Here's what will actually fail:

Adding GitHub Actions now is a time bomb. Every YAML syntax error, npm ci mismatch, Playwright browser install timeout — that's 30-90 minutes per failure. You have 26 tests. Building locally takes less than 2 minutes.

The real failure is deployment inconsistency. You have no Dockerfile for frontend or bahuraksha-api. Render's build env is a black box. Docker Compose is already a trap with two backends having profiles and frontend not containerized.

What to do: Dockerize frontend + bahuraksha-api into a single docker-compose.yml with ml-pipeline as the third service. Test docker compose up on three different machines. One manual end-to-end smoke test script. Skip GitHub Actions. Add it next semester.

The First Principles Thinker

You're asking the wrong question. The real problem isn't "what CI/CD setup" — it's "how do we not fail demo day in 7 days."

What problem does CI/CD solve between now and demo day? Nothing. CI/CD is for ongoing development velocity. You'll make maybe 3-5 bugfix commits. You don't need a pipeline — you need stability.

The only thing that matters: Build locally. Test locally. Deploy once. Freeze your deployment, don't automate it. Every minute spent on YAML is a minute not spent fixing that one flaking E2E test, making sure the model returns predictions, and rehearsing the demo flow.

If you absolutely must have CI: one file — GitHub Actions that runs lint + test + backend pytest. 20 minutes to write, zero maintenance. Docker for frontend? Delete that idea. Render already serves it.

The Expansionist

You're thinking way too small. Build a single docker compose up that runs all three services — frontend, unified API, and ML pipeline. Works offline, on any machine, zero cloud dependency. Render dies on demo day? Doesn't matter. No wifi? Doesn't matter. That's insurance, one YAML file away.

The adjacent opportunity: This isn't a class project, it's a portfolio centerpiece. Multi-service ML system with satellite ingestion, two XGBoost backends, real-time React map that deploys via docker compose up? That's the conversation starter at every interview.

What's undervalued: GitHub Container Registry (free, unlimited, tagged images). GitHub Actions matrix (parallel lint+test+build, ~3 min wall time). Render as backup, not primary. Build the Compose file, add a CI workflow that publishes to ghcr.io.

The Outsider

You have 7 days. You have 3,555 frontend modules and 14 tests. That ratio tells me you've been building features, not infrastructure. Keep doing that.

Docker is a distraction for demo day. You already deploy on Render without it. Docker adds a learning curve, a Dockerfile to maintain, another thing to debug. If Render works today, ship on Render on demo day.

Your CI should be 15 lines of YAML. GitHub Actions free tier is fine. On push to main: npm ci, npm run lint, npm run test, npm run build. Backend too: pip install, pytest. No matrix builds, no caching optimization, no Docker Compose in CI.

Simple breaks less. Complex CI breaks and you lose a day. The real risk isn't CI — it's that you're building CI instead of rehearsing your demo. Ship CI in 30 minutes. Spend 6 days 23 hours on demo quality.

The Executor

Monday morning plan:

1. Skip Docker for the frontend. Render already deploys it. A Dockerfile adds another layer of breakage for zero demo-day benefit.

2. One GitHub Actions workflow: runs on PR + push to main. Lint → test → build (parallel). No E2E in CI — free runners flake. Run E2E locally before demo.

3. For bahuraksha-api: Render auto-deploys from the repo. Add a python -m pytest step after the JS build if you want. Even that's optional.

Actual file: .github/workflows/ci.yml — 40 lines, ubuntu-latest, two jobs. Copy-paste existing npm scripts. Done in 15 minutes.

Do NOT do: Docker Compose, multi-stage builds, E2E in CI, matrix builds, Docker Hub pushes, separate staging. If it compiles and tests pass, it ships.
